## 为何要拆

`assets/css/custom.css` 是站点纸张风格覆盖层，此前是 **2016 行 / 59.4 KB 的单体文件**，导航、卡片、页脚、移动端、文章排版、关于页、留言板、投票评分全混在一起。改一处字体大小要在两千行里找归属，新加页面样式也没有明确落点，几周就会继续膨胀。

## 拆分方式

- 按文件里**既有的分区注释**逐字节切片，落到 `assets/css/custom/{foundation,layout,components,pages}/`，共 29 个分片（目录分类与主题 `assets/css/solitude/` 同构）。
- `assets/css/custom.css` 退化为**聚合根**：只保留 `@charset` 与 29 条 `@import`，导入顺序严格等于拆分前的行序。`css.Build` 会把 `@import` 内联，因此构建产物仍是**一个** `css/custom.<hash>.css` —— 请求数、首屏字节、层叠顺序全都不变。
- 主题的 `styles.html` 一行未改（`resources.Get "css/custom.css"` 与 targetPath 都保持原样），改的是源文件组织方式。

**为什么坚持「顺序即语义」**：这条覆盖层是**无 layer** 的，靠「最后加载 + 不分层」压过主题全部 `@layer solitude.*`，中间还隔着主题里未分层的 vendor 与 `overrides.css` 规则。分片一旦重排或改成 `@layer`，同权重选择器的胜负会静默翻转 —— 所以聚合根里写明了「勿重排、勿增删、勿分层」。

## 等价性验证

- **生产产物逐字节一致**：拆分前后各跑一次 `hugo --minify`，产物文件名（内容哈希）与 SHA-256 完全相同 —— 浏览器收到的字节没变，层叠结果可证明未变。
- **开发模式规则序列一致**：243 条规则对 243 条，唯一差异是构建管线按 target 自动补的 `-webkit-backdrop-filter`（拆分前的产物里也有同一条前缀），属管线行为而非拆分差异。
- **无路径泄漏**：生产产物确认不含开发模式的 `ns-hugo-imp` 批注、Windows 绝对路径与残留 `@import`。

## 新增工具：`scripts/css-split-audit.mjs`

拆分会引入一类肉眼极难发现的问题（分片漏引、文件放错位置、顺序被改），所以配了机械审计：

- 默认模式：查「聚合根 ↔ 分片目录」是否一一对应 —— 缺失 / 空片 / 孤儿文件 / 重复 `@import` / 分片内 `@charset` 或嵌套 `@import` / 聚合根里被直接写了规则。
- `--compare A B`：比对两份 CSS 产物是否等价，先比字节，不等时退化为「有序规则序列」比对，并区分「缺规则 / 多规则 / 仅顺序不同」。
- `--overlap A B`：列出两组分片共享的选择器。这条是为将来「真实按页加载」把关 —— 两组选择器不相交，它们的相对加载顺序才与层叠无关。

工具内置一个极简 CSS 扫描器（正确处理注释、字符串、未加引号的 `url()`、`@media`/`@keyframes` 嵌套），并附带 26 个 `node:test` 用例（含属性选择器引号、An+B 空白、函数参数内空白等易误报形态的归一化）。

## 兼容性与维护约定

- 未引入新依赖，未改主题，未改任何模板；CSS 片段内容除文件末尾补了一个换行外逐字节继承。
- 之后新增样式：先找归属分片，确实要新建分片就**追加到聚合根 `@import` 末尾**，并跑一次 `node scripts/css-split-audit.mjs`。约定与分片清单已写入 `docs/agents.md`。
